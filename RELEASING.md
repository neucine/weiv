# Weiv releasing

The canonical release contract is in daydream `shared/decisions/0001-canonical-release-process.md`.
The version entry points are `packages/weiv/package.json`, the three platform package manifests, the main package's optional dependencies, and `docs/site/site.json`. The macOS ARM64 binary under `packages/weiv-darwin-arm64/bin` is committed release input. Linux x64 and Windows x64 binaries are built on their release runners from the same commit. Each platform's verification checks its native binary format and packs that binary. Publish all platform tarballs before the `weivjs` tarball, then verify a fresh install on all three platforms. The VS Code extension lives in `packages/vscode-extension` and has its own Marketplace release flow.

Run `node tools/release.mjs plan --preflight-only` before expensive gates. For an offline rehearsal on a release candidate commit, run `node tools/release.mjs rehearse`; local experimentation on a dirty tree or existing version may use `--allow-dirty`. The rehearsal runs the component/runtime suite against the committed binary, checks the Vite plugin, packs npm tarballs, installs the main tarball in a local consumer, copies the verified tarballs into the local sink, checks their hashes, and renders `state/record.md`. It creates no tag or remote publication. The local component/runtime suite passed 170 tests and the Cyna suite passed 407 tests on 2026-11-10.

The Buildkite `weiv-ci` pipeline is the release route. Open a `release/vX.Y.Z` pull request with the version changed in the package and site manifests. Each commit on that branch checks the pinned Cyna distributions, verifies macOS ARM64, Linux x64, and Windows x64 candidates, and compares the packed tarballs and hashes. Fixes start a new candidate build; a failed job can be retried on the same commit.

After the pull request merges, the ordinary `main` webhook build recognizes the merged release PR and runs the three platform checks again on the merge commit. It collects the verified packages and pauses for release approval. Approving that build publishes the same collected tarballs to npm without rebuilding them, checks fresh installs on all three hosts, and creates the GitHub release. The publisher needs `NPM_TOKEN` and `GITHUB_RELEASE_TOKEN` in Buildkite. A regular `main` commit runs only the fast checks.

The same Buildkite pipeline runs formatting, runtime, UI core, and VS Code extension checks on ordinary branches and pull requests. The release build requires a Windows agent on the `windows-local` queue and Cyna distributions for all three hosts. Keep the GitHub workflows active until a Buildkite release has passed all three published install checks.

A release record belongs in `daydream/projects/weiv/docs/releases/` after publication.

After a version is published on npm and GitHub, run `node tools/sync-release-site.mjs` from the published Weiv commit. It checks the published version, syncs `docs/site/` into the separate `neucine/sites` repository, builds and deploys weiv.dev, and verifies the live site. Set `WEIV_SITES_REPO` when using an isolated sites checkout. The sites checkout must be clean and at `origin/main`; its updated content lock is committed and pushed before deployment. Add this command after public package publishing when that path is wired.
